# Analysis Plain Korean

데이터 분석 결과를 사용자가 바로 읽고 설명할 수 있는 한국어로 바꾼다. 특히 A/B 테스트, EDA, 가설검정, 리텐션 분석, 실험 결과 요약처럼 숫자와 판단이 섞인 자료에 쓴다.

## 기본 원칙

- 사실, 수치, 날짜, 표본 수, p값, 그룹명, 가설명은 바꾸지 않는다.
- "A가 이겼다", "승리", "승패"처럼 대결처럼 들리는 말은 쓰지 않는다.
- 작은 표본에서는 "확정", "검증 완료", "효과 있음"처럼 강하게 단정하지 않는다.
- 분석 용어는 필요할 때만 남기고, 먼저 쉬운 해석을 쓴다.
- 발표자가 그대로 읽어도 어색하지 않게 짧은 문장으로 쓴다.
- 사용자에게 필요한 판단은 "유지", "수정", "재검증", "보류", "해석 보정"처럼 실행 가능한 말로 정리한다.

## 문장 톤

좋은 문장은 먼저 뜻이 보여야 한다.

- "tester 단위"보다 "사람 단위"를 먼저 쓴다.
- "event 단위"보다 "같은 사람이 여러 번 만든 이벤트"처럼 풀어 쓴다.
- "공변량"보다 "해석 보정" 또는 "결과를 읽을 때 함께 봐야 할 차이"라고 쓴다.
- "p-value보다 방향성"보다 "p값은 참고값"이라고 쓴다.
- "전체 번들 승패"보다 "전체 번들 우세 여부" 또는 "A가 더 낫다고 단정할 수 있는지"라고 쓴다.

## 분석 해석 구조

슬라이드나 보고서용 문구는 보통 아래 순서로 정리한다.

1. 이 결과를 어떻게 읽어야 하는지 먼저 말한다.
2. 어떤 단위로 비교했는지 설명한다.
3. 결과가 어느 쪽으로 보이는지 말한다.
4. 왜 단정하지 않는지 짧게 적는다.
5. 다음 실험이나 제품 판단으로 연결한다.

## 권장 표현

| 피할 표현 | 바꿔 쓸 표현 |
| --- | --- |
| A가 이겼다 | A가 더 낫다고 단정하긴 어렵다 |
| 승패 | 우세 여부, 확정 결론 |
| tester 단위 | 사람 단위 |
| event/session 단위 | 이벤트 기준, 세션 기준 |
| 공변량 | 해석 보정 |
| exact permutation | 가능한 A/B 배치를 모두 비교한 순열검정 |
| p-value보다 방향성 | p값은 참고값 |
| 효과 검증 | 효과 후보, 재검증 필요 |
| 유의하지 않다 | 차이가 있다고 말하기엔 근거가 약하다 |

## 예시

원문:

> tester 단위를 우선하고, event와 session 결과는 보조 근거로 사용했습니다. 반복 이벤트는 독립 표본처럼 해석하지 않았습니다.

수정:

> 먼저 사람 단위로 봤습니다. 같은 사람이 여러 번 만든 이벤트는 여러 명의 의견처럼 세지 않았습니다.

원문:

> n=10이라 작은 차이를 승패로 말하지 않았습니다. 여러 지표가 같은 방향인지 더 중요하게 봤습니다.

수정:

> n=10이라 작은 차이를 확정 결론으로 말하지 않았습니다. 여러 지표가 같은 방향인지 더 중요하게 봤습니다.

원문:

> A는 넓게 탐색했지만 B는 시간과 재방문이 높았습니다. 전체 승리는 아닙니다.

수정:

> A는 더 이것저것 해봤지만, B는 시간과 재방문이 높았습니다. A가 더 낫다고 단정하긴 어렵습니다.

## 자체 점검

마무리 전에 아래를 확인한다.

- `승리`, `이겼다`, `승패`가 남아 있지 않은가
- 숫자와 그룹명, 가설명, p값이 원문과 같은가
- 발표자가 읽었을 때 첫 문장부터 뜻이 들어오는가
- 분석 용어를 쉬운 말보다 앞세우지 않았는가
- 결론이 과장되지 않았는가
