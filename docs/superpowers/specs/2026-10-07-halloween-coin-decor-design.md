## 1. 1부 — 탁상 올려놓기

### 1-1. 출처
커밋 `e93a8a1`(브랜치 `feat/capacitor`, 2026-09-18)은 main 에 병합된 적이 없다. 그 뒤로 `game.js` 가 `js/spaces/*` 로 분리됐고 집이 다층(1층·2층·루프탑)이 됐다. cherry-pick 은 하지 않고 diff 를 읽어 새 위치에 직접 이식한다.

### 1-2. 원본 설계 (유지)
- 높이는 세이브에 저장하지 않는다. `surfaceAt()` 이 "소품 y = 그 자리를 덮는 상판 중 가장 높은 것"을 매번 계산한다. 세이브 포맷 무변경, 받침을 치우면 소품이 저절로 바닥으로 내려온다.
- `DECOR[].top = { y, pad }` (테이블 0.66 · 큰 식탁 0.69 · 협탁 0.55 · 스툴 0.42), `sm: true` (화분·꽃병·라디오·어항·탁상 등불).
- 판정: 소품 **중심이 상판 안**이면 올라간다(가장자리 걸침 허용). 소품이 상판보다 크면 거부.
- 상판 위 소품은 `solidBox` 를 걸지 않는다. `reseatDecor()` 를 `placeDecor`·`pickDecor` 끝에서 부른다(복원 순서 무관).
- `nearestDecor` 는 상판 위 소품을 받침의 발자국으로 거리를 잰다. 동률이면 소품 우선, 받침은 직접 탭 + `firstHintBanner('decorStack')` 1회.
- 고스트·근접 링·조준 레이캐스트(상판도 대상)가 같은 높이를 따라간다.
- 🪔 탁상 등불(`deskLamp`)을 소품으로 신설, 책장·옷장·벽난로는 상판에서 제외(천장).
- i18n: `'탁상 등불': 'Table Lamp'`.

### 1-3. 개선 3종
1. **다층 대응.** 현재 코드는 레코드에 `f`(층)가 있고 `floorBaseY(f)` 가 루프탑 높이를 준다. `surfaceAt` 은 **같은 층(`rec.f`)의 상판만** 받침으로 인정하고, 소품 y = `floorBaseY(f) + 0.2 + 상판높이`. 층이 다르면 같은 x,z 라도 올라가지 않는다. `nearestDecor` 의 받침 탐색도 같은 층만 본다.
2. **순수 모듈 분리.** `js/house/surface.js` (THREE·DOM 없음): `decorHalf(foot, rot, scale)`, `surfaceAt(point, def, rot, candidates, scale)` → `{ y, hostId } | null`, `ceilingOk(topY, h, scale)`. 씬 쪽(`indoor.js`)은 후보 목록을 만들어 넘기는 얇은 어댑터만 둔다. 단위 테스트 가능.
3. **천장 높이 규칙을 테스트로 고정.** `sm` 소품마다 `h`(배율 전 높이)를 둔다. 테스트가 모든 `(top 가구 × sm 소품)` 조합에 대해 `0.2 + (top.y + h) * DECOR_SCALE < WALL_H(3)` 를 검사한다. 루프탑 층은 천장이 없으므로 제외. 이 규칙을 어기는 소품을 추가하면 테스트가 깨진다.

| 실내 | 👻 유령 촛불 | 탁상 소품(`sm`, 1부 규칙) | 150 |

가격 근거(Supabase, 2026-10-07 조회): 최근 14일 저장 326건의 보유 코인 중앙값 10 · p75 165(상위 구간은 시뮬 계정 혼입 가능). 30일 획득 — 비게스트 107명 중앙값 57 · p75 187, 활동일당 중앙값 20 · p75 61, 700 이상 번 유저 5명. 판매 창 10일 × p75 61 ≈ 610. ### 2-2. 기간 규칙 (기간 밖 = 숨김)
- 순수 함수 `catalogVisible(item, { stored, now })` (`js/shop/sale-window.js` 옆): `!item.sale || saleOpen(item, now) || stored > 0`. 안 산 사람에겐 목록에서 숨기고, **보관분이 있으면 계속 보여** 꺼내 놓을 수 있다(유료 꾸미기의 `premiumRowMode` 'owned' 원칙).
- 적용 지점 두 곳: 가구 목록(`index.html` `renderDecorItems`), 야외 작업대 목록(`renderOutdoor`). 행 태그는 `saleTagOf` 재사용(라벨은 번역 대상, 날짜는 번역 안 함 — 문장 글루 금지).
- **구매 가드**: 코인 차감은 클라이언트뿐이라 목록 숨김만으론 부족하다. `placeDecor`·`placeOutdoor` 의 **신규 구매 경로**(보관분 꺼내기·옮기기·복원·`silent` 제외)에서 `def.sale && !saleOpen(def)` 이면 토스트 후 `false`. 가게를 열어 둔 채 기간이 끝나는 경우를 막는다.
- 놓인 것(세이브)과 보관분은 기간과 무관하게 영구 유지. 내년엔 `SALE_WINDOWS.halloween` 날짜만 바꾸면 재판매.
- 야외 `hidden`(보관분 있을 때만 표시)과 의미가 다르다 — `hidden` 은 영구 비판매, `sale` 은 기간 판매. 둘을 섞지 않는다.

### 2-3. 구현 지점
- 데이터: `js/data/catalog.js` — `DECOR` 3줄(`pay:'coins'`, `sale`, `foot`, 유령 촛불은 `sm`+`h`), `OUTDOOR` 3줄(`cost:{coins:N}`, `sale`).
- 외형: 실내 `js/spaces/indoor.js` `decorMesh(id)` 분기 3개, 야외 `js/game.js` `outdoorMesh(id)` 분기 3개. 새 모델 코드가 크면 `js/spaces/` 아래 별도 파일로 뺀다(`game.js` 에 몰지 않는다).
- 야외 코인 구매 기록: 야외는 코인 로그가 없다 → `logEcon('outdoor_buy', id, -N, balance)` + `trackEvent('outdoor_buy_coins', { item, coins, sale })` 추가(실내의 `decor_buy` 와 같은 축). 새 `source` 값이 `econ_logs` 에서 받아지는지 구현 단계에서 확인.
- i18n: `js/i18n-en.js` 이름 6개 + 설명.
- 묘비 울타리는 **밤손님 방어 울타리로 치지 않는다**(`fence` 판정에 포함하지 않음 — 밸런스 변경 방지). 구현 시 판정 코드가 id 를 어떻게 세는지 확인.

### 2-4. 조형 제약
- 메시 ≤3(재질별 병합), 블룸 임계 0.85(발광 재질이 번지지 않게), 면 겹침 줄무늬·작은 소품 그림자 지글거림 주의(`noShadow`), 기존 집/마당 팔레트에 맞춘다.
- 밤 광원은 세기·색·**광원 자리** 3종 세트로 확인(유령 촛불·유령 정원등).
- 드로우콜은 실측(1부·2부 각각 전/후).

## 3. 작업 순서와 승인 게이트

1. 이 spec 승인 → `writing-plans` 로 구현 계획.
2. **1부**: TDD(surface.js 테스트 먼저) → 이식 → 게임 안 실측(탁자 위 놓기·들기·받침 제거·2층·루프탑) → 코드 리뷰 → 커밋.
3. **2부 시안**: 상품마다 2~3안을 PC·모바일로 나란히 렌더(self-contained HTML — 워크트리는 preview 가 루트를 띄운다) → **사용자 승인 후** 구현. 시안 전에 **한국어 이름·설명 후보를 먼저 검수**받는다.
4. 2부 구현 → 밤·낮 캡처 · 드로우콜 · 전체 `npm test` · 코드 리뷰 · **푸시 전 비밀 스캔(공개 저장소)**.
5. 배포는 사용자 지시 시에만(4곳 동시).
