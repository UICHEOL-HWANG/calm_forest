## 1. 무엇을 만드는가

게임 안에서 **"이 세션이 곧 끝날 것 같다"**를 실시간으로 판정하고,
그 순간에 **비차단 배너로 다음 행동을 제시**한다. A/B로 개입 효과를 잰다.

**만드는 진짜 이유는 통계가 아니라 공학이다.** 어려운 건 모델이 아니라 파이프라인
(피처 추출 · 실시간 서빙 · A/B 하네스 · 결과 회수)이고, 이건 표본 크기와 무관하게
지금 만들어야 나중에 데이터가 쌓였을 때 갈아끼우기만 하면 된다.
**모델 출력을 검증된 것처럼 믿지 않는다** — §9 참조.

## 2. 왜 세션 단위인가 — 기기 단위는 예측 불가

의도적 행동을 한 기기 81대 중 **79대(97.5%)가 결국 이탈**했다.
행동별로 봐도 전부 95~100%다(퀘스트 수락 100% · 벌목 97.9% · 수확 95.7%).

**기기 단위 라벨에는 분산이 없다.** "이탈하나"를 예측하면 무조건 "예"가 97.5% 맞는다.

| 단위 | 라벨 | 분포 | 쓸 수 있나 |
|---|---|---|---|
| 기기 — 결국 안 옴 | 3일 무복귀 | 79 : 2 | ❌ |
| **세션 — 곧 끝남** | span < 180초 | **393 : 185** | ✅ |

세션 단위만 68:32로 분산이 있다.

> ⚠️ `02` 노트북 9절의 "행동별 멈춤 비율"(NPC 대화 46%)은 **위험도가 아니라
> 그 행동이 마지막이 될 확률**이다. 다들 어차피 이탈하므로 그 비율은 게임 흐름상
> 그 행동이 얼마나 뒤에 있느냐를 반영한다. 위험 지점으로 읽으면 안 된다.

## 3. 트리거 — 언제 판정하는가

### 3-1. 시간 트리거: 접속 후 15초

세션의 **84%(578/688)**가 15초까지 생존한다. 15초 시점에 쌓인 좌표는 중앙값 12행,
서로 다른 시각 6개(≈2.5초 해상도)로 피처 계산에 충분하다.

`created_at`이 배치 삽입 시각이지만 배치가 1.5초 주기라, 15초 잘라내기엔 해상도가 남는다.

**15초 전에 나가는 16%(110세션)는 못 잡는다.** 설계상 수용한다.

### 3-2. 행동 트리거: 퀘스트 계열 접촉

> 🔴 **2026-09-04 정정.** 아래 표는 처음에 **세션 기준**으로 쟀던 것을 **이벤트 기준**으로 다시 잰 것이다.
> 세션 기준("이 세션이 그 행동을 했고, 그중 한 번이라도 직후에 끝났나")은 **자주 하는 행동을 자동으로 부풀린다** —
> 세션당 6.9회 하는 NPC 대화는 끝에 걸릴 기회가 7번, 1.2회 하는 집 완성은 1번이기 때문이다.
> 실시간 개입은 **행동할 때마다** 판정하므로 이벤트 기준이 맞는 셈이다.
> 처음 표(수락 49.1% · 완료 47.1% · NPC 46.4% · 집 완성 15.4%)는 **쓰지 않는다.**

**기준선 — 아무 순간이나 찍었을 때 60초 안에 세션이 끝날 확률: 8.9%**
(GA4 전체 이벤트 18,427건, 120초 넘게 논 세션만. 짧은 세션은 뭘 해도 곧 끝나 비율을 부풀린다.)

같은 조건에서 행동별 — 이벤트 하나하나가 한 건:

| 행동 | 60초 내 종료 | 기준선 대비 | 남은 시간 중앙값 | 이벤트 수 |
|---|---|---|---|---|
| **퀘스트 수락** | **16.6%** | **1.9배** | 331초 | 193 |
| **퀘스트 완료** | **14.2%** | 1.6배 | 292초 | 127 |
| **NPC 대화** | **12.8%** | 1.4배 | 384초 | 374 |
| 집 완성 | 12.5% | 1.4배 | 459초 | 48 |
| 나무 베기 | 9.7% | 1.1배 | 577초 | 1,945 |
| *(아무 순간)* | *8.9%* | *1배* | *752초* | *18,427* |

**결정: 셋을 그대로 하나의 트리거로 묶는다(안 B).** 이벤트 694건.

묶는 근거가 처음과 달라졌다. 처음엔 "셋의 신뢰구간이 서로 겹쳐서"였는데,
실제로는 **셋 다 기준선과도 겹친다** — 표본이 48~374건이라 오차 범위가 넓다.
확실히 기준선 위인 것은 **퀘스트 수락 하나뿐**이다(1.9배).

그런데도 셋 다 쓰는 이유:
- 손해가 작다 — 틀려도 비차단 배너 하나다
- 기회가 193건 → 694건으로 늘어 A/B 에서 볼 게 생긴다
- `trigger` 종류를 로그에 남기므로(§9) **나중에 어느 것이 실제로 효과가 있었는지 갈라 볼 수 있다**

> 퀘스트가 이탈을 **만든다**는 뜻은 아니다. 한 덩어리가 끝나서 자연스럽게 나가는 것일 수 있다.
> 그래도 "다음에 뭐 할래" 가 들어갈 자리로는 유효하다.

⚠️ **처음 표의 "남은 시간 중앙값 61초"는 재현되지 않는다.** 이벤트 기준으로는 292~384초다.
낚시(404초)와의 격차도 처음 생각만큼 크지 않다.

### 3-3. GA4 ↔ game_logs 조인 키는 `user_id` 다 (2026-09-04 확인)

한때 "이을 열쇠가 없어 시간으로 근접 매칭할 수밖에 없다"고 적었으나 **틀렸다.**
GA4 퀘스트 이벤트의 90%(647/720)에 `user_id` 가 실려 있고, `game_logs` 에도 같은 컬럼이 있다.

| | |
|---|---|
| uid 있는 퀘스트 이벤트 | 508건 |
| **정확히 한 세션에 붙음** | **466건 (91.7%)** |
| 안 붙음 | 36건 (7.1%) |
| 두 세션에 걸침 → 버린다 | 6건 (1.2%) |

`user_id` 는 익명 로그인이 **세션마다 재발급**하므로 사실상 세션 식별자다(uid당 세션 1.05개).
그 회전은 리텐션 분석에서 함정이고 `CHURN_ANALYSIS_PLAN.md` 가 "user_id 금지"라고 경고한 이유지만,
**그 경고는 리텐션에 한정된다.** 세션 안에서 두 기록을 잇는 데는 오히려 딱 맞는 성질이다.

## 4. 라벨과 피처

**라벨은 하나로 통일한다** — 트리거 시점 기준 **그 뒤 60초 안에 세션이 끝나는가**(1 = 끝남).

두 트리거가 서로 다른 라벨을 쓰면 한 모델로 학습할 수 없다. 15초 트리거도
"15초 시점부터 60초 안에 끝나는가"로 맞춘다. 사전등록의 `span_sec < 180` 은
세션 전체 길이 기준이라 이 설계와 축이 다르므로 쓰지 않는다 —
그쪽 기준으로 낸 결과는 §12 의 모델 판정에서만 병기한다.

**피처** — 트리거 시점까지 쌓인 좌표에서 계산. 사전등록 §4의 7개를 그대로 쓰고 하나만 추가한다.

| # | 피처 | 계산 |
|---|---|---|
| 1 | `path_len` | 연속 좌표 거리 합 |
| 2 | `net_disp` | 첫 좌표 → 마지막 좌표 직선 거리 |
| 3 | `wander_ratio` | `path_len / NULLIF(net_disp, 0)` |
| 4 | `yaw_total` | `cam_yaw` 변화량 절대값 합 |
| 5 | `mouse_travel` | 마우스 이동 거리 합 |
| 6 | `idle_ratio` | 직전과 좌표가 같은 행의 비율 |
| 7 | `is_first_session` | 이 클라이언트의 첫 세션인가 |
| 8 | `trigger_kind` | `time15` / `quest` — 트리거 종류 |

**누수 금지** — `span_sec`, 총 행 수(`pts`), `session_logs` 의 종료 시점 값은 피처로 쓰지 않는다.

## 5. 학습 — Airflow DAG, 주 1회

VM 이 이미 Airflow 를 돌리고 있으므로 학습은 DAG 로 넣는다. 손으로 돌리는 스크립트가 아니다.

```
Airflow DAG (주 1회)
BigQuery ─▶ 피처·라벨 추출 ─▶ L2 로지스틱 ─▶ coef.json ─▶ /opt/calm-api/model/
                                   └─▶ W&B 런 기록          (API 가 mtime 보고 핫리로드)
```

- 표본: 578세션. **클라이언트당 5세션 상한을 적용한다**(~300세션) —
  상위 3개 클라이언트가 세션의 37%를 차지해 상한 없이는 그 3명의 습관을 배운다.
  상한 없는 판도 같이 학습해 **강건성 확인용으로 병기**한다(주 결과는 상한 적용판)
- 검증: `GroupKFold(client_id)` 5-fold, 부트스트랩 1,000회 CI
- 베이스라인 2개: ① 다수 클래스 ② `path_len` 단일 피처
- 산출물은 `ml/notebooks/04_churn_model.ipynb` 에 기록
- DAG 는 `infra/airflow/dags/churn_train.py`. 배포는 기존과 동일하게 scp

## 6. 추론 — 오라클 VM 의 FastAPI

**결정: VM 에 FastAPI 를 올린다.** 서빙 파이프라인을 직접 만드는 것이 이 프로젝트의 목적이고
(§1 — "만드는 진짜 이유는 공학"), 그 경험은 계수를 JS 상수로 박아서는 생기지 않는다.

```
클라이언트  피처 8개 계산 (좌표·시선은 클라이언트에만 있다)
   │  POST https://lab.calmforest.cloud/predict   { features, trigger, session_id, variant }
   ▼
nginx ─▶ uvicorn:8100  계수 dot product + sigmoid → p
                       임계값·on/off·model_version 도 여기 (클라이언트 배포 없이 조정)
                       피처+점수 적립 ──▶ 다음 주 학습 표본 (§9)
   │  { p, intervene, model_version }
   ▼
클라이언트  intervene 이면 showHintBanner (문구는 규칙으로 — §7)
```

**자원은 문제가 아니다** — 실측 2 vCPU · RAM 11Gi 중 **9.6Gi 여유**, CPU 거의 idle.
Airflow 3개 컨테이너가 1.7Gi 를 쓰고 있고 uvicorn 은 150MB 수준이다.
연산도 곱셈 8번 + `exp()` 한 번이라 부하가 아니다.

**대신 치르는 값 — 알고 간다**

| | |
|---|---|
| 크로스 오리진 | 게임은 Cloudflare, API 는 `lab.calmforest.cloud`. `POST`+JSON 이라 **preflight 왕복 2회** |
| 단일 호스트 | 이중화 없는 VM 하나. 재부팅·다운 시 기능 정지 — fail-open 이라 **조용히** 멈춘다 |
| 토스 웹뷰 | 앱인토스에서 이 오리진 호출이 되는지 **확인 필요**(미확인 항목) |

**완화** — 클라이언트 타임아웃 800ms, 실패 시 개입 없이 진행(fail-open), 미응답도 로그로 남긴다.
배너 하나 못 띄우는 것이 손해의 전부이므로 이 값은 치를 만하다.

**기각한 대안 둘**

- **계수를 JS 상수로**(`js/model-coef.js`) — `dist-toss` 가 별도 번들이라 모델 갱신이
  토스 번들 재업로드·심사에 걸린다. 주 1회 재학습과 앞뒤가 안 맞는다
- **Cloudflare Worker** — 운영상으로는 이쪽이 최선이다(동일 오리진·이미 요청 경로에 있음).
  순수하게 서빙을 직접 만들어보기 위해 택하지 않았다. **운영이 아파지면 여기로 옮긴다**

기존 `ml/api/main.py` 스텁은 타깃이 `d1_return_prob` 이라 이번 설계와 다르다 — 교체한다.

## 7. 개입

**무엇을 띄울지는 모델이 아니라 규칙이다.** 미완 여부는 `gameState` 에 사실로 들어 있어
추정할 이유가 없다.

```
1순위  미완 짚기      심었는데 물 안 줌 · 받아놓고 안 한 퀘스트 · 지을 수 있는 집
2순위  다음 할 것      아직 안 해본 것 중 흔한 것 (전역 인기순)
```

**표시는 기존 `showHintBanner` 재사용** — 비차단, 5.5초 자동 소멸. 오탐이 나도 손해가 작다.
세션당 최대 노출 횟수를 `tuning.js` 로 제한한다.

> 추천 모델은 만들지 않는다. 의도적 행동 세션 216개 · 세션당 행동 종류 중앙값 1개라
> "A 다음 B" 를 배울 전이가 없다. 상위 동시등장 쌍도 `chop_tree`+`first_chop` 처럼
> 같은 행동이 두 번 찍힌 것이다.

## 8. A/B 설계

**전원 점수화, 처치군만 개입.** 그래야 모델이 아니라 **개입 효과**가 측정된다.

- 배정은 기존 `state.variant` 재사용(베타 명단 테이블)
- 파라미터는 `js/tuning.js` 에 — 임계값 · 개입 on/off · 세션당 최대 노출
- **규칙 베이스라인을 같이 기록한다** — "트리거 도달 = 무조건 개입" 이 모델을 이기는지
  나중에 비교할 수 있게, 모델 점수와 규칙 판정을 둘 다 로그로 남긴다

## 9. 측정

**학습 표본은 API 가 적립한다.** 이게 서버를 두는 실질 이득이다 —
판정에 **실제로 쓴** 피처 값이 그대로 쌓이므로 학습/서빙 스큐가 원천 차단된다.
(계수를 JS 에 박고 GA4 로만 남기면, 학습 때 SQL 로 재구성한 피처와
서빙 때 JS 가 계산한 피처가 갈릴 수 있다.)

요청 경로를 느리게 하지 않도록 **적립은 로컬 → 배치**로 한다:
API 가 로컬(postgres 또는 JSONL)에 append → Airflow DAG 가 야간에 BQ 로 올린다.

GA4 이벤트는 A/B 분석용으로 병행한다.

```js
trackEvent('churn_score', { p, trigger, rule, variant, shown, threshold, model_version })
```

이탈 여부는 기존 `game_logs` 의 `span_sec` 으로 사후 계산하므로 별도 계측이 필요 없다.

**모델 성능은 A/B 의 판정 대상이 아니다.** 점수만 기록해 두고, 표본이 쌓이면 그때
사전등록 §5 기준(AUC 95% CI 하한 > 0.60)으로 따로 판정한다.

## 11. 알고 시작하는 것

- **표본 578세션**(상한 적용 시 ~300). 트리거별 건수는 34~56
- **모델이 규칙을 못 이길 수 있다.** 그래서 둘 다 기록한다
- **15초 전 이탈 16%는 못 잡는다**
- **상위 3개 클라이언트가 세션의 37%** — 개발자 기기로 의심되나 확인 안 됨
- **베타 10명으로는 개입 효과의 유의성이 안 나온다**(검정력 ~7%). 방향성 참고용
- **퀘스트 트리거의 인과는 미확인** — 퀘스트가 이탈을 만드는지, 끝나서 나가는지 안 갈린다
- **활동 순서는 복원 불가**(기기 95% 타임스탬프 동률). 시퀀스 피처는 쓸 수 없다
- **퀘스트 이벤트의 14%는 학습에 못 쓴다** — uid 없음 + 세션에 안 붙음 + 애매. 720건 중 616건만 남는다
- **`/predict` 가 열려 있으면 학습 테이블이 오염된다** — 적립처를 겸하므로 최소 방어 필요(§6 미결)
- **VM 단일 호스트 의존** — 다운되면 개입이 조용히 멈춘다. 헬스 확인 수단이 있어야 한다
