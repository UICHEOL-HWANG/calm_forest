# 🏔️ 설산 — 등산·썰매·정상 전망대·얼음 낚시 설계

- 작성: 2026-10-15
- 상태: 설계 확정(사용자 승인 완료), 구현 계획 작성 전
- 시안: `dev/active/mountain-sled/mockup.html?v=a|b|c`, 비교표 `dev/active/mountain-sled/shots/compare.png`

## 0. 목표와 범위

마을 북쪽 원경에 구름 낀 설산을 두고, 이틀째 접속부터 들어갈 수 있는 산 공간을 연다. 산 안에는 세 가지 활동이 있다.

1. **썰매 한 판**: 뒤 능선으로 오르며 🌰 도토리를 줍고, 정상에서 앞 사면을 S자로 활강한다.
2. **📸 정상 전망대**: 한 판 중 정상에서 사진을 찍어 사진첩을 채운다.
3. **❄️ 얼음 낚시**: 산기슭 언 호수에서 깊이를 골라 낚시한다.

목적은 속도감 있는 장르 추가, 2일 차 복귀 이유, 겨울 공지·광고 소재 확보다. 첫 세션 경험(E1·E2 실험, 광고 퍼널)은 건드리지 않는다.

### 단계

| 단계 | 내용 | 단독 출시 |
|---|---|---|
| 1 | 원경 + 산 공간 + 등산 + 썰매 + 기록판 | 가능 |
| 2 | 정상 전망대·사진첩 | 가능 |
| 3 | 얼음 낚시(낚시 로직 일반화 포함) | 가능 |

단계마다 검증하고 출시한다. 새 세이브 키·도감 id 가 생기는 단계는 4곳 동시 배포다(§5.1).

## 1. 확정된 결정

| 항목 | 결정 |

| 수집물과 썰매 | 수집물 한 종류(🌰 도토리), 모은 개수만큼 활강 중 부스터 사용 |
| 맵 배치 | 뒤 능선으로 오르고 앞 사면으로 S자 활강(두 길이 겹치지 않음) |
| 외관 | 중턱 구름 띠, 앞 사면 가운데는 썰매 코스가 보이게 비움(시안 A) |
| 해금 | 이틀째 접속부터. 계절 무관, 사계절 썰매 |

| 얼음 낚시 조작 | 기존 낚시 조작 + 얕게/깊게 선택, 깊이마다 어종이 다름 |

## 2. 마을 원경과 입구

### 2.1 원경

- 형태: 넓게 퍼진 원뿔, 위 절반은 눈 덮인 능선(골짜기를 따라 눈 줄기가 내려옴), 그 아래 어두운 바위 띠, 기슭은 숲. 플랫 셰이딩 저폴리, 색은 버텍스 컬러.
- 구름: 중턱 높이(산 높이의 약 0.38)에 뭉게구름 띠. 앞 사면 가운데(카메라 쪽 약 ±0.38 rad)는 비운다. 아주 천천히 회전.
- 드로우콜: 산 1 + 구름 띠 1 = **2콜**(시안 실측).
- **제약**: 게임 카메라 far=200, 안개 18~74(`js/game.js` 씬 초기화). 그대로 두면 원경이 보이지 않는다.
  - 원경은 `fog: false` 재질로 만들고, far 안쪽(약 150~180)에 축소 배치한다.
  - 마을에 있을 때만 보이고, 다른 공간에 들어가면 숨긴다. 마을 −z 축에 안개 숲(−250)·강(−400)·꿈의 숲(−550)·거울 마을(−700)이 있어 겹치지 않게 하기 위함이다.
- **가시성 검증(1단계 첫 작업)**: 플레이 카메라는 내려다보는 시점이라 원경이 화면에 얼마나 들어오는지 PC·모바일 가로·세로로 캡처해 확인한다. 거의 안 보이면 다음으로 보완한다.
  - 해금되는 날 카메라가 산 쪽을 한 번 비추는 연출
  - 미니맵·전체 지도에 산 아이콘

### 2.2 입구

- 마을 북쪽 끝에 산길 입구(`MOUNTAIN_GATE`). 정확한 좌표는 기존 시설(선착장 `DOCK_GATE` (0,−15), 나루터 연못)과 겹치지 않는 자리로 구현 때 정한다.
- 해금 전에는 입구에 "내일 열려요" 팻말만. 해금은 첫 접속일 다음 날부터(`gameState` 의 첫 접속일 기준).
- 해금 당일 하루 1회 안내 배너. 글자 안내는 HUD 자리에만(월드 말풍선은 이모지만 규칙).

## 3. 산 공간

### 3.1 위치와 동선

- 공간 원점 `MOUNTAIN = (0, 0, −1000)`. 거울 마을(−700)과 충분히 띄운다.
- 입구로 들어가면 **산기슭 광장**에 도착한다. 길이 둘로 갈린다.
  - 왼쪽: ❄️ 언 호수(얼음 낚시)
  - 오른쪽: 뒤 능선 등산로(썰매 한 판 시작)
- 광장 남쪽에 나가는 문.

### 3.2 썰매 한 판(약 1분 30초)

1. **오르기(약 40초)**: 산을 돌아 뒤 능선길을 걷는다. 🌰 도토리 최대 6개. 일부는 길에서 살짝 벗어난 곳에 둬서 고르는 재미를 준다. 중간에 구름 띠를 내려다보는 경치 포인트 1곳.
2. **정상(약 5초)**: 앞 사면이 트이는 연출. 📸 전망대(§3.3)를 거친 뒤 썰매 탑승, 3·2·1 카운트다운.
3. **활강(35~45초)**: S자 사면.
   - 조향: 화면 왼쪽/오른쪽 반쪽을 누르고 있는 동안 그쪽으로 튼다. PC 는 ←→ 또는 A/D.
   - 부스터: 버튼(PC 스페이스) 1회 = 도토리 1개 소모, 2초 가속. 버튼은 모바일 액션 버튼 자리를 재사용하고 남은 도토리 수를 표시.
   - 깃발 게이트 약 12개. 놓치면 기록 +1초.
   - 눈덩이·바위 충돌은 잠깐 감속만, 판은 끝나지 않는다.
4. **결과**: 완주 시간, 개인 최고 기록, 오늘 남은 보상 판수(3판 중 N), 정상 기록판 순위.

수치(도토리 수, 부스터 배율·지속, 감속량, 깃발 페널티, 보상 코인)는 위 값을 출발점으로 두고, 구현 전에 시뮬레이션으로 확정한다(바다 낚시와 같은 절차).

### 3.3 📸 정상 전망대

- 한 판 중 정상에서 사진 한 장. 건너뛸 수 있다.
- 장면은 시간대·날씨로 정해지고 사진첩에 모인다. 초기 장면 5종: 맑은 낮, 노을, 밤 별, 운해 아침, 눈 오는 날.
- 새 장면을 처음 찍으면 소량 보상. 같은 장면 재촬영은 보상 없음.
- 운해 아침 장면은 원경 시안 C(산 아래 운해)를 아침 연출로 재사용한다.

### 3.4 ❄️ 얼음 낚시

- 산기슭 언 호수. 높은 곳이라 사계절 얼어 있다.
- 조작은 기존 호수 낚시와 같고, 캐스트 전에 **얕게/깊게**를 고른다.
- 어종 4종(도감 `DEX.fish` 에 추가, 마을 호수의 겨울 한정 `얼음 빙어` 와 겹치지 않음):

| 깊이 | 어종 | 희귀도 |
|---|---|---|
| 얕게 | ❄️ 눈송이 피라미 | 흔함 |
| 얕게 | 산천어 | 조금 귀함 |
| 깊게 | 열목어 | 조금 귀함 |
| 깊게 | 🌟 별빛 곤들매기 | 아주 귀함 |

- 하루 보상 상한은 썰매와 별도로 둔다(수치는 시뮬레이션으로 확정).

## 4. 코드 구조와 성능

### 4.1 파일

game.js 에는 게이트·액션·미니맵 훅 몇 줄만 더한다. 새 코드는 아래로 나눈다.

| 파일 | 역할 |
|---|---|
| `js/data/places.js` | `MOUNTAIN`, `MOUNTAIN_GATE`, 얼음 호수 좌표 상수 |
| `js/spaces/mountain.js` | 공간 진입·나가기, 광장, 해금 판정, 원경 표시 전환 |
| `js/mountain/backdrop.js` | 마을 원경(산 + 구름 띠) |
| `js/mountain/terrain.js` | 공간 안 지형, 능선길, S자 사면 |
| `js/mountain/course.js` | 깃발·장애물·도토리 배치 데이터(`course_v`) |
| `js/mountain/climb.js` | 오르기와 도토리 수집 |
| `js/mountain/sled.js` | 활강 물리·조향·부스터·충돌 감속(`phys_v`) |
| `js/mountain/sled-run.js` | 판 정산: 보상 상한, 기록, GA4·Supabase 기록 |
| `js/mountain/overlook.js` | 전망대와 사진첩 |
| `js/mountain/ice-fishing.js` | 얼음 구멍, 깊이 선택, 어종 표 |
| `js/spaces/fishing.js` | 낚시터 설정(물 위치·반경·어종 표·깊이)을 인자로 받도록 일반화 |

- 낚시 일반화는 기존 호수 동작을 그대로 유지해야 한다. 기존 낚시 테스트를 먼저 통과시킨 뒤 얼음 호수를 붙인다.
- `sled-run.js` 는 천문대 `js/observatory/star-run.js` 의 정산 구조(판 시작·정산·하루 보상·`run_id`)를 따른다.

### 4.2 드로우콜 예산

- 마을 원경: 2콜.
- 산 공간 안: 60콜 이하. 지형은 재질별 병합, 나무·깃발·바위·눈덩이·도토리·얼음 구멍은 종류마다 `InstancedMesh` 1개.
- 산 공간에 있는 동안 마을 섀도맵·렌더를 멈춘다(기존 섀도 정지 방식).
- 단계마다 `renderer.info` 와 모바일 프레임을 실측한다.

## 5. 데이터

### 5.1 세이브

`gameState.mountain`:

| 키 | 내용 |
|---|---|
| `sled.best` | 개인 최고 기록(ms) |
| `sled.plays` | 누적 판수 |
| `sled.daily` | `{ date, rewarded }` 오늘 보상 받은 판수 |
| `photos` | 찍은 장면 id 목록 |
| `ice.daily` | 얼음 낚시 하루 보상 카운트 |

- 도토리는 판 안에서만 쓰는 값이라 저장하지 않는다.
- 얼음 어종 4종을 도감에 추가하면서 도감 전체 수와 박물관 전시도 갱신한다.
- 새 세이브 키와 도감 id 가 생기므로 **4곳(웹·토스·Play·iOS) 동시 배포**. 옛 클라이언트가 모르는 키를 지울 수 있다.

### 5.2 정상 기록판과 `sled_runs`

판 1회 = 1행(완주·포기 포함). Supabase 에만 기록하고 GA4 파라미터 한도와 무관하다.

| 그룹 | 컬럼 |
|---|---|
| 식별 | `run_id`, `user_id`, `created_at`, `platform`, `is_persona`, `is_dev` |
| 결과 | `outcome`(finish/abandon), `abandon_stage`, `time_ms`, `flags_passed`, `penalty_ms`, `rewarded` |
| 판 내부 | `splits` jsonb(깃발별 `[통과 여부, 도달 ms]` 12쌍), `boosts_at` jsonb(부스터 사용 시점), `hits` jsonb(충돌 시점·종류), `steer_left_ms`, `steer_right_ms` |
| 판 직전 맥락 | `attempt_n`, `days_since_unlock`, `best_before_ms`, `acorns_available`, `acorns_collected`, `climb_ms`, `photo_taken` |
| 환경 | `input`(touch/keys), `orientation`, `fps_avg` |
| 버전 | `course_v`, `phys_v` |
| 실험 | `arm`, `ease`, `dda`, `probe_v` |

- 기록판 순위는 로그인 계정의 완주 기록만. 페르소나·관리자·dev 세션 제외(기존 리더보드 규칙).
- RLS 는 `(select auth.uid())` 규칙. DDL 은 풀러로 직접 실행한다.
- jsonb 컬럼에는 크기 CHECK 를 건다(보안 보강 규칙). 판당 1KB 미만 예상.
- 이론 최단 기록(코스 버전별)보다 빠른 기록은 서버 트리거로 거부한다.
- **원본 영구 보존**. 정리 작업 대상에서 제외한다(대시보드 원본 7일 보존 함정 회피).

### 5.3 얼음 낚시 캐스트 기록

- 캐스트 단위로 남긴다: 잡기·놓치기·걷기 전부, `depth`, 결과, 대기 시간.
- 기존 `fishing_catch`·`fishing_miss`·포기 이벤트에 `spot`(lake/ice)과 `depth` 를 더한다.

## 6. GA4 트래킹

| 이벤트 | 코드 키 | 자동 키 | 합계/25 |
|---|---|---|---|
| `mountain_enter` | 첫 방문 여부 1~2 | `ts`, `platform` | 4 이하 |
| `sled_start` | `run_id`, `attempt_n`, `course_v` 등 3~4 | 2 | 6 이하 |
| `sled_result` | 기록, 깃발, 부스터, 도토리, `run_id` + 난이도 4 | 2 | 11 |
| `overlook_photo` | 장면 id, 새 장면 여부 | 2 | 4 |
| `fishing_catch` | 기존 8 + `spot`, `depth` | `ts`, `platform`, `exp_arm` | 13 |

- 중간 이탈은 기존 `minigame_abandon` 을 쓴다.
- 배열·구간 기록은 GA4 에 넣지 않고 `sled_runs` 에만 남긴다.
- 키 이름은 `run_id`, `attempt_n` 등 기존 키를 우선 쓰고, 새 키는 `spot`, `depth`, `flags`, `boosts` 정도로 줄인다.
- `ga-params` 테스트에 새 이벤트 4종의 실제 payload 가 25개 이하라는 단언을 넣는다.
- 배포 다음 날 BigQuery 에서 `ga_param_overflow` 0건과 새 키 적재를 확인한다.

## 7. 머신러닝 활용 준비

| 용도 | 쓰는 데이터 |
|---|---|
| 난이도 맞춤(DDA) | `arm`·`ease`·`dda`·`probe_v`(무작위 배정), 결과, 맥락 |
| 구간별 막힘 분석 | `splits`, `hits`, `course_v` |
| 이탈·리텐션 피처 | `days_since_unlock`, `attempt_n`, 하루 판수, 사진첩·낚시 활동 |
| 부정 기록 탐지 | `boosts_at`, 조향 시간, `splits` 간격, 이론 최단 기록 |
| 깊이 선택 행동 | 얼음 낚시 캐스트 기록 |

- 썰매에도 기존 난이도 probe(`rollDifficulty`)를 적용해 무작위 배정을 남긴다.
- 수치를 튜닝하면 `course_v`·`phys_v` 를 올린다. 버전이 섞인 학습은 금지.
- `is_persona`·`is_dev` 로 학습 데이터에서 제외할 수 있다.
- Airflow 에 `sled_features_daily` 마트를 추가해 기존 이탈·리텐션 모델(W&B) 피처로 연결한다.
- 한계: 구간별 모델과 DDA 는 판 수천 개가 필요하다. 출시 후 몇 주 누적을 전제로 한다. 나중에 컬럼을 추가하면 그 전 데이터는 되돌릴 수 없으므로 처음부터 전부 남긴다.

## 8. 테스트와 검증

- 단위: 활강 물리(조향·부스터·충돌 감속), 깃발 판정, 하루 3판 보상 상한, 이틀째 해금 판정, 깊이별 어종 추첨, 사진 장면 판정.
- 회귀: 낚시 일반화 뒤 기존 호수 낚시 테스트 전부 통과.
- GA4: 새 이벤트 payload 25개 이하 단언.
- 실측: 원경 가시성 캡처(PC·모바일 가로·세로), 드로우콜(원경 2, 공간 60 이하), 모바일 프레임.
- 수치 시뮬레이션: 도토리 수, 부스터, 보상 코인, 얼음 낚시 확률을 구현 전에 확정.
- 배포 다음 날: BigQuery 에서 새 이벤트와 `sled_runs` 적재 확인.
