# 🎚️ 미니게임 난이도 probe + 유저별 자동 조절 — 설계

- 날짜: 2026-09-22
- 브랜치: `feat/difficulty-probe` (main `406ce70` 기준)
- 관련: [[feature-tracking-checklist]] 8번 · `docs/beta/BETA_AB_TEST_PLAN.md` · `js/tuning.js`

## 1. 문제

미니게임 난이도를 **재튜닝할 근거가 없다.**

2026-09-21에 발견한 대로, 난이도 배율 `ease`(`js/tuning.js` `easeMult`)가 어느 결과 이벤트에도
실려 있지 않다. 더 근본적인 문제는 **값이 안 흔들린다**는 것이다. `easeMult(variant, tries)`는
결정론적 함수이고 값이 `1.0`/`1.3` 둘뿐이며, `1.3`은 베타 A군 4~5명의 미니게임당 최초 3회뿐이다.
분산이 사실상 0이라 로깅을 고쳐도 전부 같은 값만 쌓인다.

누락(기록을 빠뜨린 것)이 아니라 **변동이 없어 배울 게 없는** 문제다. DDA·개인화·밴딧이 전부
같은 조건에 걸린다.

## 2. 측정된 현황 (30일, `session_logs.counts`)

| 게임 | 이벤트 | 표본 | 결과 형태 | 현재 성적 |
|---|---|---|---|---|
| 🍳 요리 | `cooking_result` | 31판 (× 스테이지 × 탭 = **수백 탭**) | 연속 점수 0~100 | 미측정 |
| 🌫️ 안개 | `mist_soothe` / `_miss` | 45탭 | 이진 | **80%** (36/45) |
| 🌊 바다 | `sea_catch` / `sea_miss` | 35캐스트 | 이진 | **40%** (14/35) |
| 🎣 낚시 | `fishing_catch` / `_miss` | 25캐스트 | 이진 | **96%** (24/25) |
| ⚔️ 승부 | `duel_start` | 6 | 이진 | `duel_logs` 0행 |
| 🔥🫙 가공 | `craft_set` | 3 | 연속 점수 0~1 | 미측정 |
| 🗿 조각 | `carve_start` | 2 | 연속 점수 0~100 | 미측정 |

⚠️ `craft_item` 29건은 도구·시설·선물 **제작**이지 가공 미니게임이 아니다. 혼동하지 말 것.

두 가지가 설계를 좌우한다.

1. **유저 단위 A/B는 불가능하다.** 7일 세션 108건 / 유저 72명 — 유저당 플레이가 1회꼴이라
   유저를 나누면 개인차가 난이도 효과를 통째로 덮는다. 배정은 **판(시도) 단위**여야 한다.
2. **표본은 요리에 있다.** 요리·가공은 결과가 연속 점수라 이진 승패보다 표본 효율이 몇 배 높다.
   낚시는 이진인 데다 96%라 측정 대상으로는 최악이다.

## 3. 목표 / 비목표

**목표**

- 미니게임 난이도 상수를 **어디로 옮길지** 2주 안에 답을 낸다.
- 유저별로 난이도가 자동 조절되고, 그 궤적이 데이터로 남는다.
- 모든 미니게임이 **같은 손잡이 하나**를 쓴다.

**비목표**

- 난이도 → 리텐션 인과 추정 (유저 72명으로는 검정력이 없다)
- 실력 추정 모델 · 밴딧 · ML (유저당 플레이 1회로는 개인 실력을 못 뽑는다)
- 새 Supabase 테이블 (재튜닝은 2주 관찰이라 BigQuery 하루 지연이 문제가 안 된다.
  `duel_logs`를 급히 만들었다가 0행으로 남은 전례도 있다)

## 4. 설계

### 4-1. 손잡이 하나로 통일

기존 `easeMult`의 의미(**클수록 쉽다**)를 그대로 확장한다. 미니게임은 계수 `e` 하나만 받는다.

```
e = clamp(e_dda × e_probe, 0.35, 2.5)
```

`e_dda`는 유저별로 **천천히 미끄러지는 바닥**, `e_probe`는 그 위에서 **판마다 튀는 지터**다.
이 순서여야 한다 — probe가 DDA 출력 위에 독립적으로 곱해지므로, DDA가 유저마다 다르게
움직여도 probe 효과는 편향 없이 추정된다. 반대로 DDA가 probe 결과를 보고 반응하게 만들면
인과 추정이 망가진다.

### 4-2. 게임별 적용 지점

| 게임 | 손잡이 | 적용 | 수정 위치 |
|---|---|---|---|
| 🍳 요리 | 스테이지 판정창 `mult` | `mult × e` | `courseOf` (game.js:10244) |
| 🌫️ 안개 | 판정창 하한 `1 − 0.38×e` | 이미 이 형태 | game.js:7164 |
| 🌊 바다 | `sp.tap × e`, `sp.drag ÷ e` | 이미 이 형태 | game.js:7925, 7932 |
| 🎣 낚시 | 입질창 `(2.6\|1.4) × e` | 이미 이 형태 | game.js:13271 |
| 🔥 숯 | `fireScore(half)` | `half × e` | index.html:4029 |
| 🧱 벽돌 | `knead2Score(tol)` | `tol × e` | index.html:4069 |
| 🍷 포도 | `crushScore(tolRatio)` | `tolRatio × e` | game.js:2104 |
| ⚔️ 승부 | shells `ms` | `ms × e` | 2차 |
| 🗿 조각 | `dmgMax` 3 | 이산값 — 1차 제외 | — |
| 🌾 맷돌 | **없음** | 제외 | — |

**요리는 `index.html`을 안 고친다.** 네 미니게임이 이미 `cfg.mult`를 판정창 배율로 쓰고
(index.html:4250, 4292, 4349, 4404), `cfg`는 `courseOf()`가 만든 스테이지 객체다. game.js에서
`mult × e` 하면 끝난다.

**맷돌(`millScore`)은 난이도 상수가 없다.** 각속도의 변동계수로 점수를 내는 구조라 흔들 값이
없다. 판정 임계(`gradeOfScore`)를 흔드는 건 성격이 다른 변경이라 제외한다.

### 4-3. probe — 판마다 순회

관측 성적이 방향을 이미 알려주므로 팔을 비대칭으로 둔다. 반대쪽 팔은 표본 낭비다.

| 게임 | 팔 0 | 팔 1 | 팔 2 | 근거 |
|---|---|---|---|---|
| 🎣 낚시 | 0.45 | 0.65 | 1.0 | 96% — 어려운 쪽만. 1.4초 → 0.63 / 0.91 / 1.4초 |
| 🌊 바다 | 1.0 | 1.5 | 2.2 | 40% — 쉬운 쪽만 |
| 🌫️ 안개 | 0.7 | 1.0 | 1.3 | 80% — 적정, 양방향 |
| 🍳 요리 | 0.7 | 1.0 | 1.4 | 연속 점수, 양방향 |
| 🔥🫙 가공 | 0.7 | 1.0 | 1.4 | 연속 점수, 양방향 |

배정은 무작위 추첨이 아니라 **유저별 무작위 시작점 + 판마다 순회**다.

```
arm = (hash(uid) + n) % 3        // n = 그 게임의 누적 시도 수
```

70판 규모에서 균등 추첨은 팔별로 20/31/19처럼 쏠리지만, 순회는 유저 안에서도 팔이 고르게
떨어진다. `hash(uid)`로 시작점을 흩어 "모든 유저의 첫 판이 팔 0"이 되는 걸 막는다.

**요리는 코스가 아니라 스테이지 단위로 순회한다.** 한 판(★3이면 3스테이지) 안에서도 팔이
갈려 표본이 서너 배가 된다.

### 4-4. DDA — 목표 추적 컨트롤러

판이 끝날 때마다:

```
e_dda ← clamp(e_dda + k × (목표 − 결과), 0.7, 1.5)
```

`결과`는 0~1로 정규화한다 (이진은 성공 1 / 실패 0, 점수 게임은 점수/만점).
성공하면 계수가 내려가 어려워지고, 실패하면 올라가 쉬워진다. 목표로 수렴하는 표준 형태다.
`k = 0.10`.

| 게임 | 목표 | 현재 | 1차 적용 |
|---|---|---|---|
| 🎣 낚시 | 성공률 0.88 | 0.96 | 적용 |
| 🌊 바다 | 성공률 0.55 | 0.40 | 적용 |
| 🌫️ 안개 | 성공률 0.80 | 0.80 | 적용(유지) |
| 🍳 요리 | 점수 0.65 | 미측정 | **1주 차 미적용** |
| 🔥🫙 가공 | 점수 0.65 | 미측정 | **1주 차 미적용** |

**목표값은 잠정치다.** 적정 성공률이 얼마인지는 우리가 모르는 값이고, 그걸 알아내라고 probe를
도는데 DDA가 먼저 그 값으로 몰고 가면 순서가 거꾸로다. 그래서 1차에는 목표를 관측값 근처에
두고 clamp를 `0.7~1.5`로 좁게 걸어 DDA가 **꼬리만 잡게** 한다 — 계속 놓치는 사람을 구제하고
한 번도 안 놓치는 사람을 조인다. 요리·가공은 현재 점수 분포조차 모르므로 1주 차엔 DDA를 끄고
probe만 돌려 분포를 먼저 본다.

**알려진 비용**: DDA는 모두를 목표로 끌어당겨 성공률 분산을 줄이므로 probe 추정이 둔해진다.
표본 70회 규모에선 공짜가 아니다. 그래서 DDA를 probe보다 느리게(작은 `k`, 좁은 clamp) 둔다.

### 4-5. 로깅

결과 이벤트에 세 필드를 추가한다. GA4 예약 파라미터(`source`·`medium`·`campaign`·`term`·
`content`)와 겹치지 않는다.

| 필드 | 뜻 |
|---|---|
| `ease` | 최종 계수 `e` (소수 둘째 자리) |
| `dda` | `e_dda` 단독값 — 유저별 난이도 궤적 |
| `arm` | probe 팔 인덱스 0/1/2 |

적용 이벤트: `fishing_catch` · `fishing_miss` · `sea_catch` · `sea_miss` · `mist_soothe` ·
`mist_soothe_miss` · `cooking_result` · `cooking_abandon` · `craft_set`.

요리는 이미 `offsets`(탭별 원본 타이밍) · `n_perfect/good/miss` · `stage_scores`를 남긴다.
여기에 세 필드만 더하면 탭 단위 분석이 바로 된다. 요리는 스테이지마다 팔이 다르므로
`arm`·`ease`를 **스테이지별 배열**(`arms: "0,1,2"`, `eases: "0.7,1.0,1.4"`)로 보낸다.

새 Supabase 테이블은 만들지 않는다.

### 4-6. 세이브

```js
gameState.difficulty = {
  fish:  { dda: 1.0, n: 0 },
  sea:   { dda: 1.0, n: 0 },
  mist:  { dda: 1.0, n: 0 },
  cook:  { dda: 1.0, n: 0 },
  craft: { dda: 1.0, n: 0 },
}
```

`n`은 probe 순회용 누적 시도 수. 기존 `gameState.beta.tries`와 역할이 겹치지만 `tries`는
베타 A/B 전용이라 건드리지 않고, 필드 없는 옛 세이브는 기본값으로 뜬다
(`js/save-migrate.js` 패턴을 따른다).

## 6. 검증

`js/difficulty.js`가 순수 함수이므로 테스트로 잠근다.

1. 순회가 3판마다 세 팔을 모두 준다
2. `hash(uid)`가 다르면 시작 팔이 흩어진다
3. 진짜 실력이 `p`인 가상 플레이어를 1,000판 돌리면 `e_dda`가 목표 쪽으로 수렴한다
4. clamp 경계에서 멈춘다
5. `difficulty` 필드 없는 옛 세이브가 기본값으로 뜬다
6. 요리 스테이지 배열의 길이가 코스 길이와 같다

배포 다음 날 BigQuery에서 `ease`·`dda`·`arm`이 실제로 찍히는지 확인한다
([[feature-tracking-checklist]] 5번 — GA4 export는 되돌릴 수 없다).

## 7. 함정

- **로컬에선 트래킹 발화를 못 본다.** dev 파라미터(`?spawn=`·`?weather=`)가 있으면
  `trackEvent`가 맨 앞에서 반환하고, 빼면 **프로덕션 GA4로 나간다**. 검증은 배포 후 BQ에서.
- **`index.html`의 요리 미니게임은 `cfg.mult`만 본다.** 거기에 `e`를 또 곱하면 이중 적용된다.
  `courseOf`에서 한 번만 곱할 것.
- **낚싯대 업그레이드(`2.6`)와 곱해진다.** 팔 번호가 절대 난이도를 뜻하지 않는다 — 업글 유저의
  가장 어려운 팔 0(`2.6 × 0.45 = 1.17초`)이 미업글 유저의 가장 쉬운 팔 2(`1.4초`)보다 **짧다**.
  분석에서 `rod` 업글 여부를 반드시 갈라 보고, 비교는 팔 번호가 아니라 **실제 입질창 초**로 할 것.
- **비 오는 날 낚시는 입질이 빨라진다**(`RAIN_DAY`). 입질창과는 다른 축이지만 체감에 섞인다.
- **요리 `mult`는 스테이지마다 다르다**(`COURSE_MULT`). `e`는 그 위에 곱하는 것이지
  대체하는 게 아니다.
