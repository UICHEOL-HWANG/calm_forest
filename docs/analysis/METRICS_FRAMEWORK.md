# 🌟 calm forest 지표 체계 — 북극성 · 지표 트리

**작성** 2026-10-08 · **상태** 정의 확정, 계산(M5)·계측 감사(M4) 대기
**작업 기록** `dev/active/metrics-framework/` (후보 전수·검증 원본·결정 로그)

## 1. 목적

"이번 주 calm forest 가 나아졌나?"에 숫자 하나와 그 숫자를 움직이는 레버 몇 개로 답한다.

| 우선순위 | 답하려는 질문 |
|---|---|
| 1 | 사람들이 이 게임을 **매일 잠깐씩 습관처럼** 다시 찾는가 |
| 2 | 새로 온 사람이 게임의 재미(첫 결과물)까지 도달하는가 |
| 3 | (품질 기준) 측정 방법이 설명 가능하고 엄밀한가 |

## 2. 북극성 지표

> **하루 평균 가꾼 주민 수** (Daily Tending Villagers)
> 지난 7일 동안 "가꾼 하루"를 보낸 (주민 × 날)의 수 ÷ 7

| 요소 | 규칙 |
|---|---|
| 주민 | 로그인 계정 = `user_id`, 게스트 = `client_id`. 게스트 기기가 나중에 로그인하면 그 기기의 과거 기록을 계정으로 합친다 |
| 하루 | KST 자정 기준, 세션 시작 시각 |
| 가꾼 하루 | 아래 **결과물 행동** 중 1회 이상 |
| 표시 | 7일 이동 평균. 주간 보고는 그 주 값 |
| 모집단 | **공식** = 페르소나·개발자 제외, 베타테스터는 베타 기간(9/9~9/15)만 제외 · **원본** = 필터 없음. 항상 나란히 표시 |
| 플랫폼 | 웹 · 토스. 안드로이드(로그 없음)·itch(결과물 0)는 계측 수정 후 편입 |

### 결과물 행동 16종

| 분야 | 이벤트 |
|---|---|
| 농사 | `harvest_crop` 수확 · `coop_collect` 달걀 · `honey_collect` 꿀 |
| 낚시·채집 | `fishing_catch` · `sea_catch` · `firefly_catch` · `forage_pick` · `mine_ore` |
| 만들기 | `craft_item` 제작 · `craft_claim` 밤사이 가공 수령 · `cooking_result` 요리 · `cafe_serve` 카페 · `carve_result` 조각 |
| 마을 | `quest_complete` 퀘스트 · `star_result` 천문대 · `duel_result` 밤손님 |

**뺀 것과 이유**
- `dex_discover` — 수확·낚시의 부산물, 같은 행동을 두 번 셈
- 스토리·튜토리얼·집 완성 — 1회성 진행, 습관이 아님
- `cook_eat` — 소비 행동
- 물 주기·파종·벌목 — 결과물이 생기지 않음 (사용자 결정: "무언가를 손에 쥐고 나간 날")
- 꾸미기·잡담 — 근거 §7 V2 (활동일의 4.3%, 재방문율도 낮음)

## 3. 계산 구조

```
session_logs ─▶ 공통 필터 ─▶ 주민 키 통합 ─▶ (주민×날) 가꾼 여부 ─▶ 7일 평균 ─▶ 공식 값
                                                                         └▶ 원본 값 (필터 없이)
GA4 events  ─▶ 같은 정의 ───────────────────────────────────────────▶ 그림자 값 (대조용)
```

- **공식 원천 = `calm_forest_raw.session_logs`** (session_id 별 최신 행의 `counts` JSON). 혼합 키에 필요한 `user_id`·`client_id`·`is_guest` 가 한 행에 다 있는 유일한 원천
- **그림자 = GA4 `events_*`**. 같은 정의를 이벤트 단위로 계산해 계측 이상을 감지
- SQL 위치: `sql/analytics/metrics/` — 공통 필터 1 · 북극성 1 · 대조 1 (담당 Codex)
- 출력 열: `period, platform, variant(official|raw), value, numerator, denominator`

## 4. 운영 규칙

| 규칙 | 내용 |
|---|---|
| **재계산** | 키 통합 때문에 과거 값이 바뀔 수 있다 → 매번 전체 재계산, 보고에 계산일 표기 |
| **그림자 경보** | 로그인 계정 기준 SL↔GA4 가꾼 (주민×날) 일치율이 **95% 미만 2주 연속**이면 계측 점검 (기준선 98.4%) |
| **목록 추가** | 새 결과물 행동은 추가일을 변경 기록에 남기고 차트에 세로선. 과거 재계산 없음 (과거엔 없던 행동) |
| **목록 삭제** | 과거까지 재계산 |
| **읽기** | 주간 등락은 해석하지 않는다. **의미 있는 변화 = 최근 4주 평균이 직전 4주 값의 95% CI 밖**. 차트엔 항상 CI 띠 |

## 5. 지표 트리

### 분해식 (항등식)

```
북극성 × 7  =  주간 방문 주민 수  ×  1인당 방문일  ×  방문일 중 가꾼 비율
                   (폭)              (빈도)             (품질)
```

북극성이 움직이면 세 요인 중 어디서 움직였는지 정확히 나뉜다.

| 단계 | 지표 | 정의 | 목표 |
|---|---|---|---|
| **NSM** | 하루 평균 가꾼 주민 수 | §2 | 습관 |
| **L1 폭** | 주간 방문 주민 수 | 그 주 세션이 1개 이상인 주민 | |
| └ L2 | 신규 | 그 주가 첫 방문 | 활성화 |
| └ L2 | 유지 | 지난주에도 방문 | 습관 |
| └ L2 | 복귀 | 2주 이상 공백 후 방문 | 습관 |
| **L1 빈도** | 1인당 방문일 | 방문일 합 ÷ 방문 주민 | 습관 |
| └ L2 | 습관 주민 비율 | 주 4일 이상 방문한 주민 ÷ 방문 주민 | 습관 |
| **L1 품질** | 방문일 중 가꾼 비율 | 가꾼 (주민×날) ÷ 방문 (주민×날) | 습관 |
| └ L2 | 분야별 결과물 비중 | 농사·낚시채집·만들기·마을 | |
| └ L2 | 빈손 방문의 마지막 위치 | 결과물 0 인 날의 `last_place` 분포 | |
| **활성화** | 7일 내 첫 결과물 비율 | 신규 중 첫 7일 안에 가꾼 날 ≥ 1 | 활성화 |
| └ L2 | 첫 결과물까지 시간 | 첫 세션 시작 → 첫 결과물 이벤트 | 활성화 |

활성화는 **신규 → 유지** 사이의 다리다. AARRR 의 Activation·Retention 은 이 트리를 그대로 쓴다 (M3).

### 견제 지표

| 지표 | 막으려는 것 |
|---|---|
| 빈손 방문 비율 (= 1 − 품질) | 출석 보상 같은 장치로 방문만 부풀리기 |
| 코인 순증가 속도 (`econ_logs` 획득 − 사용, 주민당) | 결과물을 쉽게 만들려는 보상 남발 → 경제 인플레 |
| 세이브 실패율 (`save_load_failed` ÷ 로드 시도) | 지표가 오르는 동안 데이터 유실 같은 품질 사고가 묻히기 |

## 6. 정한 것과 이유 (결정 기록)

| 결정 | 선택 | 이유 |
|---|---|---|
| 목표 | 습관 > 활성화 > 엄밀성 | 사용자 결정 |
| 리듬 | 매일 잠깐 | 출석·일일 의뢰·밤사이 가공 등 게임 설계가 하루 주기 |
| 가꾼 날 기준 | 결과물이 생긴 날 | 사용자 결정 — 켜기만 한 날·물만 준 날 제외 |
| 사람 키 | 혼합 (계정/기기) | 토스 = 계정이 정확, 웹 게스트 = 기기뿐 |
| 묶는 방식 | 합계형 (사람×날 ÷ 7) | 폭과 빈도를 한 숫자에. 문턱형·비율형은 L2/L1 로 |
| 모집단 | 공식 + 원본 병기 | 제외 효과를 숨기지 않음 |
| 원천 | SL 공식 + GA4 그림자 | 혼합 키는 SL 에서만 가능, GA4 로 계측 이상 감지 |
| 플랫폼 | 웹·토스 | 안드로이드·itch 는 계측 결함 |

## 7. 데이터 근거

검증은 지표를 **고르는** 용도가 아니라 고른 정의가 **측정 가능한지** 확인하는 용도로만 쓴다.
원본: `dev/active/metrics-framework/nsm-validation-results.md` (기준은 실행 전 커밋 8aec0b3·fd600ad 에 고정)

| 확인 | 결과 | 반영 |
|---|---|---|
| 정의가 놓치는 가치 (V2) | 꾸미기·잡담만 한 날 4.3%, 7일 재방문 37.5% vs 가꾼 날 59.8% | 결과물 기준 유지 |
| 계측 신뢰성 | 로그인 계정 GA4 가꾼 날 316일 중 SL 일치 98.4% | SL 을 공식 원천으로 |
| 사람 세기 (V3) | 게스트→로그인 이중 계수 5.6% (필터 후 10.8%) | 키 통합 규칙 추가 |
| 노이즈 | 주간 값 1.0~8.3 에 95% CI 반폭 0.6~3.2 | 4주 읽기 규칙 |
| 페르소나 영향 | 9/28 주 21.3 → 필터 후 1.9 | 공식 값에 필터 필수 |

**판단 근거에서 뺀 것:** V1(첫 주 가꾼 날 vs 접속일의 재방문 예측 AUC). 접속일과 재방문은 같은 것을 두 번 재는 설계라 접속 기준이 구조적으로 이긴다. 북극성은 예측력 경쟁이 아니라 가치 판단으로 고른다. 결과(SL 0.775 vs 0.847, GA4 0.712 vs 0.827)는 원본 문서에 그대로 남긴다.

## 9. 예상 질문과 답

| 질문 | 답 |
|---|---|
| 왜 WAU 가 아닌가 | 켜기만 해도 센다. 사람 키에 따라 값이 2~5배 다르다 |
| 왜 매출이 아닌가 | 현재 0 이고 결과 지표다. 지금 단계의 병목은 습관 |
| 접속일이 재방문을 더 잘 예측하던데 | 접속은 습관의 양, 결과물은 그 습관이 가치를 줬는지. 목표는 가치 있는 습관이다. 결과물 없는 방문은 견제 지표로 따로 본다 |
| 수확 1번과 천문대 1번이 같나 | 하루에 했는지만 본다. 가중치가 개입할 자리가 없다 |
| 버튼을 연타하면 부풀지 않나 | (주민×날) 단위로 0/1 이라 반복해도 1 |
| 왜 올랐나/떨어졌나 | 분해식으로 폭·빈도·품질 중 어디인지 나눠 답한다 |
| 주간 값이 튀었는데 | 주간 등락은 노이즈 범위. 4주 기준선 밖일 때만 변화로 본다 |
| 페르소나·베타는 | 공식 값에서 빼고, 원본을 옆에 둔다. 차이가 곧 제외 효과 |
| SL 과 GA4 가 다르면 | 공식은 SL. 로그인 계정 일치율 95% 미만 2주 연속이면 계측 점검 |
