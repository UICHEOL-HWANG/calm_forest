## 1. 목적

### 프로젝트 주제 한 문장

> calm forest에 처음 온 플레이어의 59%가 첫 주에 온보딩을 하거나 잠깐 둘러보기만 하고 수확·물고기 낚기·퀘스트 완료 같은 획득 행동 없이 떠나며, 이들의 2~3주 차 재방문율은 2.0%로 획득 행동을 한 플레이어(15.9%)의 8분의 1에 그친다.

| 첫 7일(0~6일차)에 | 인원 | 8~21일차 재방문 |
|---|---|---|
| 획득 행동 1번 이상 | 69 | 11 (15.9%) |
| 획득 행동 0번 | 99 (59%) | 2 (2.0%) |
| └ 온보딩까지만 (캐릭터·인트로·튜토리얼) | 43 | 첫 주 참여 시간 중앙값 14초 |
| └ 둘러보며 시도 (주민 대화 28·의뢰 제안 23·벌목 16·의뢰 수락 16·씨 뿌리기 12) | 54 | 중앙값 1.0분 |
| └ 로그인·출석 기록뿐 | 2 | — |

- 대상: 게임 개시부터 — 첫 진입 2026-07-27~09-16 신규 168명 (진입 = GA4 에 `user_id` 가 처음 생긴 날, 게스트 포함), 웹·토스, 페르소나·개발자 제외, ID 통합 · 원천 GA4 (활성화 퍼널·참여 LTV 와 같은 코호트 원천) · 스크립트 `dev/active/metrics-framework/validation/new_user_first_week_ga4.py`
- **인과 아님.** 첫 주 방문일이 같은 사람끼리 봐도 차이는 남지만(1일 방문 11.1% vs 1.1%, 2일+ 25% vs 17% — 2일+ 미획득은 6명뿐) 관찰 비교다. "첫 획득을 앞당기면 재방문이 는다"는 A/B 로 검증할 **가설**이다
- 재방문 양성 13명 — 표본이 작다
- 참여 시간은 GA4 `engagement_time_msec`(화면이 앞에 있을 때만 누적) — 실제 체류보다 짧게 잡힌다. 크기 비교용으로만 쓴다
- 이전 값(첫 접속 8/6~9/16, session_logs, 145명: 57% · 3.6% vs 16.1%)은 개시 첫 열흘이 빠진 집단이라 교체 (2026-10-11)
- 여기 첫 주 획득 비율 41%(69/168)와 §5-1 활성화 39%(79/203)는 **집단이 다르다**: 주제 문장은 21일차까지 관찰하려고 첫 진입 9/16 까지·사람 단위, 퍼널은 7일만 보면 돼 첫 방문 9/27 까지·기기(GA4 `user_pseudo_id`) 단위

### 지표 체계의 목적

"이번 주 calm forest 가 나아졌나?"에 숫자 하나와 그 숫자를 움직이는 레버 몇 개로 답한다.

| 우선순위 | 답하려는 질문 |
|---|---|
| 1 | 사람들이 이 게임을 **매일 잠깐씩 습관처럼** 다시 찾는가 |
| 2 | 새로 온 사람이 게임의 재미(첫 획득 행동)까지 도달하는가 |
| 3 | (품질 기준) 측정 방법이 설명 가능하고 엄밀한가 |

## 2. 북극성 지표

> **하루 평균 수확·포획·제작한 유저 수** (Daily Harvest·Catch·Craft Users)
> 지난 7일 동안 "획득한 하루"를 보낸 (유저 × 날)의 수 ÷ 7

| 요소 | 규칙 |
|---|---|
| 유저 | 로그인 계정 = `user_id`, 게스트 = `client_id`. 게스트 기기가 나중에 로그인하면 그 기기의 과거 기록을 계정으로 합친다. **단 한 기기에 로그인 계정이 2개 이상이면 합치지 않는다** (누구 기록인지 모름). 구현 `validation/person_key.py` |
| 하루 | KST 자정 기준 — session_logs 는 세션 시작 시각, GA4 는 이벤트 시각 |
| 획득한 하루 | 아래 **획득 행동** 중 1회 이상 |
| 표시 | 7일 이동 평균. 주간 보고는 그 주 값 |
| 모집단 | **공식** = 페르소나·개발자 제외, 베타테스터는 베타 기간(9/9~9/15)만 제외 · **원본** = 필터 없음. 항상 나란히 표시 |
| 페르소나 | 계정 이메일이 `persona-…@<시뮬 전용 도메인>` 인 계정 (Supabase `auth.users`). 시뮬레이터 실행 기록 811판의 계정 125개와 정확히 일치. 이메일은 BQ 에 없으므로 계산 시 로컬 목록으로 적용 (저장소에는 커밋하지 않음). ~~P1: 기기 4대+ & 9/28 이후~~ — 정밀도 100%·재현율 80%(10/7 이후 계정 25개 누락)로 폐기. 단 검증 스크립트는 10/7 이전 기간만 다루므로 이 조건을 이메일 목록 대신 써도 결과가 같다 |
| 개발자 기기 | 한 번이라도 `localhost`/`127.0.0.1` 에서 게임을 연 기기(`churn_events.origin`)의 모든 세션 — 12대·세션 66개(9/6~9/29). GA4 쪽은 그 기기에서 생긴 `user_id` 로 제외 |
| 플랫폼 | 웹 · 토스. 안드로이드(로그 없음)·itch(획득 행동 0)는 계측 수정 후 편입. **GA4 에서 platform 속성이 비어 있으면 웹으로 본다** |

### 획득 행동 16종

| 분야 | 이벤트 |
|---|---|
| 농사 | `harvest_crop` 수확 · `coop_collect` 달걀 · `honey_collect` 꿀 |

## 3. 계산 구조

```
session_logs ─▶ 공통 필터 ─▶ 유저 ID 통합 ─▶ (유저×날) 획득 여부 ─▶ 7일 평균 ─▶ 공식 값
                                                                         └▶ 원본 값 (필터 없이)
GA4 events  ─▶ 같은 정의 ───────────────────────────────────────────▶ GA4 대조값
             └▶ 코호트 지표 (주제 문장·활성화 퍼널·참여 LTV) · session_logs 이전 기간(7/27~8/5)
```

- **공식 원천 = `calm_forest_raw.session_logs`** (session_id 별 최신 행의 `counts` JSON). ID 통합에 필요한 `user_id`·`client_id`·`is_guest` 가 한 행에 다 있는 유일한 원천
- **대조값 = GA4 `events_*`**. 같은 정의를 이벤트 단위로 계산해 계측 이상을 감지
- **GA4 를 주 원천으로 쓰는 곳:** ① session_logs 가 없는 7/27~8/5 (기간형 지표, `user_id` 로 session_logs 사람과 이음) ② 코호트 지표 전부 — 첫 방문부터 이벤트 단위로 추적해야 하고, 60초 미만 방문도 담아야 해서
- SQL 위치: `sql/analytics/metrics/` — 공통 필터 1 · 북극성 1 · 대조 1 (담당 Codex)
- 출력 열: `period, platform, variant(official|raw), value, numerator, denominator`

## 4. 운영 규칙

| 규칙 | 내용 |
|---|---|
| **재계산** | ID 통합 때문에 과거 값이 바뀔 수 있다 → 매번 전체 재계산, 보고에 계산일 표기 |
| **대조 경보** | 로그인 계정 기준 SL↔GA4 획득한 (유저×날) 일치율이 **95% 미만 2주 연속**이면 계측 점검 (기준선 98.4%) |
| **목록 추가** | 새 획득 행동은 추가일을 변경 기록에 남기고 차트에 세로선. 과거 재계산 없음 (과거엔 없던 행동) |
| **목록 삭제** | 과거까지 재계산 |
| **읽기** | 주간 등락은 해석하지 않는다. **의미 있는 변화 = 최근 4주 평균이 직전 4주 값의 95% CI 밖**. 차트엔 항상 CI 띠 |

## 5. 지표 트리

### 분해식 (항등식)

```
북극성 × 7  =  주간 방문 유저 수  ×  1인당 방문일  ×  방문일 중 획득 비율
                   (폭)              (빈도)             (품질)
```

북극성이 움직이면 세 요인 중 어디서 움직였는지 정확히 나뉜다.

| 단계 | 지표 | 정의 | 목표 |
|---|---|---|---|
| **NSM** | 하루 평균 수확·포획·제작한 유저 수 | §2 | 습관 |
| **L1 폭** | 주간 방문 유저 수 | 그 주 세션이 1개 이상인 유저 | |
| └ L2 | 신규 | 그 주가 첫 방문 | 활성화 |
| └ L2 | 유지 | 지난주에도 방문 | 습관 |
| └ L2 | 복귀 | 그 주 방문자 중 신규도 유지도 아닌 나머지 (§5-0 정의 1) | 습관 |
| **L1 빈도** | 1인당 방문일 | 방문일 합 ÷ 방문 유저 | 습관 |
| └ L2 | 파워 유저 비율 | 주 4일 이상 방문한 유저 ÷ 방문 유저 | 습관 |
| **L1 품질** | 방문일 중 획득 비율 | 획득한 (유저×날) ÷ 방문 (유저×날) | 습관 |
| └ L2 | 분야별 획득 비중 | 농사·낚시채집·만들기·마을 | |
| └ L2 | 획득 없는 방문일의 마지막 위치 | 획득 행동이 0 인 날의 `last_place` 분포 | |
| **활성화** | 7일 내 첫 획득 행동 비율 | 신규 중 첫 7일 안에 획득한 날 ≥ 1 | 활성화 |
| └ L2 | 첫 획득 행동까지 시간 | 게임 진입(첫 `user_id` 이벤트) → 첫 획득 행동 이벤트, 7일 안 (현재 중앙값 2.1분 — §5-0) | 활성화 |

활성화는 **신규 → 유지** 사이의 다리다. AARRR 의 Activation·Retention 은 이 트리를 그대로 쓴다 (M3).

### 가드레일 지표

| 지표 | 막으려는 것 |
|---|---|
| 획득 없는 방문일 비율 (= 1 − 품질) | 출석 보상 같은 장치로 방문만 부풀리기 |
| 코인 순증가 속도 (`econ_logs` 획득 − 사용, 경제 활동 기기당) | 획득을 쉽게 만들려는 보상 남발 → 경제 인플레. ⚠️ 기기당 평균은 상위 3대가 52~97% 를 만든다(§5-5 C1) → 중앙값·상위 3대 비율 병기 권고 |
| **복구되지 않은 세이브 실패** (`save_load_failed` 가 났는데 같은 세션에 `save_load_recovered` 가 없는 세션 수) | 지표가 오르는 동안 마을을 잃는 품질 사고가 묻히기. 자동 복구되는 일시 오류(토큰 만료)는 세지 않는다 |

### 이야기 장 퍼널 · 눈의 가지(5장) 배포 후 장 번호

배포일: 배포 때 기록. 배포일부터 `story_chapter_start` · `story_chapter_complete` 의 `n` 은 5 이상 장에서 한 칸씩 밀린다(5 = snowbranch 「얼어붙은 가지」, 옛 5장은 6). 새 5장이 4장 다음에 끼어들기 때문이다. 장을 비교할 때는 `n` 이 아니라 `chapter` id 로 묶는다. 배포 전에 5장 이상을 끝낸 세이브는 배포 때 한 번만 옮겨지며 `story_migrated { from, to }`(옛 장 수 → 새 장 수)가 찍힌다. 설산 썰매지기 대화와 선물은 `keeper_talk_open { stage }` · `keeper_talk_close { stage, via, lines_seen }` · `keeper_gift { item_id }` 로 본다.

배포일부터 세계수 생명 % 의 분모가 5 가지에서 6 가지로 바뀐다. 기존 플레이어의 생명 막대와 GA4 `life` 파라미터는 배포 직후 약 17% 내려가 보이는데, 실제 진행이 줄어든 것이 아니다.

`story_migrated` 는 옮긴 세이브가 저장되기 전에 다시 접속하면 부팅 때마다 반복해 찍힐 수 있다. 유저 수를 셀 때는 이벤트 수가 아니라 기기 수로 센다.

## 5-3. LTV — 참여 LTV (가치 단위 = 획득한 날)

현금이 아니라 **게임이 유저에게서 실제로 얻는 것** — 북극성 단위인 획득한 날 — 으로 생애 가치를 잰다. 현금 결제는 0건(`purchases` 비어 있음, 2026-10-10 확인)이라 금전 LTV 는 결제가 열린 뒤 연결식으로 잇는다.

| 항목 | 정의 |
|---|---|
| **참여 LTV(k)** | 신규 유저 1명이 진입 후 k일(0~k−1일차) 동안 쌓은 **획득한 날** 수. k = 7·14·28 (코호트 규칙 §5-6) |
| 대상 | 공식 값 규칙(§2) 그대로 (단 베타 9/9~9/15 제외는 적용 안 함 — 코호트 지표) · 28일을 다 관찰할 수 있는 코호트만 |
| 활성화 비교 | 0~6일차는 활성화 정의에 들어가므로 **8~28일차만** 비교 (동어반복 방지) |
| 금전 LTV (결제 후) | 참여 LTV × **획득한 날 1일당 매출** — 결제 원장 BQ 적재(§5-2 공백 1) 후 |
| 지표 체계 위치 | 북극성의 레버가 아니라 **장기 결과 지표**. ① 활성화 가치를 크기로 말할 때 ② 광고 집행 시 유입 비용(CAC) 기준선 |
| **유입 채널 축** | 신규마다 첫 유입 채널 1개. 아래 판정 순서대로 먼저 맞는 것 |
| 추천 가치 귀속 | 추천한 유저의 가치 = 자기 참여 LTV + **데려온 유저들의 참여 LTV** (추천인 기준 합산, 피추천인 본인 LTV 는 `친구 추천` 행에 그대로) |
| 비용 연결 | 메타 광고: 경로 LTV 와 **진입 유저 1명당 광고비(CAC)** 를 나란히 → 결제 전에는 "획득한 날 1일당 광고비" · 친구 추천: 현금 비용 0, 대신 보상 지급 수를 비용 칸에 기록 |

## 5-6. 코호트 정의 (2026-10-12)

분석마다 사전등록에 따로 적던 코호트 규칙을 하나로 모은다. **이 절은 앞으로의 분석과 E1·E2 판정에 적용**하고, 이미 판정한 분석(§5-4·§5-5)과 산출한 베이스라인은 사전등록 모집단 그대로 둔다 (아래 "기존 수치").

| 항목 | 규칙 | 이유 |
|---|---|---|
| 시작 이벤트 (0일차) | **진입** — GA4 에 그 사람의 `user_id`(익명 포함)가 처음 생긴 날 (§5-0 정의 3) | 지금 코호트 분석 대부분이 실제로 이 기준. 방문 → 진입은 퍼널의 앞 단계로 따로 본다 (사용자 결정) |
| 일차 | 진입한 KST 달력일 = 0일차, 다음 날 = 1일차. "첫 7일" = 0~6일차 | 기간형 지표의 하루(KST 자정)와 같은 경계 |
| 사람 | 기간형과 같은 ID 통합(§2) — 게스트 기기가 나중에 로그인하면 계정으로 합침 | 한 사람을 두 코호트에 넣지 않으려고 |
| 묶음 | 진입 주 = 진입일이 속한 달력 주(월~일, §5-0 정의 5) | 기간형 분해와 같은 주 |
| 성숙 규칙 | k일 지표는 **k일을 다 관찰할 수 있는 코호트만** — 진입일 + k ≤ 데이터 마지막 날 | 덜 자란 코호트가 섞이면 값이 낮게 나온다 (LTV 에만 적혀 있던 규칙을 전체로) |
| 공식 모집단 | 페르소나·개발자 제외(§2) + **베타 테스터 계정은 베타 기간(9/9~9/15)에 진입했으면 코호트에서 제외** | 기간형(M5)과 같은 규칙 — 베타 보상 1.5배를 받은 사람이 신규 행동을 왜곡 (사용자 결정) |
| 베타 코호트 | 공식에서 뺀 베타 테스터는 `beta` 코호트로 **따로** 출력 (지우지 않음) | M5 `beta` 출력과 같은 방식 |
| 플랫폼 귀속 | 0~6일차 중 처음으로 비어 있지 않은 platform (M5) · 비어 있으면 웹 | 첫 화면이 아니라 실제로 쓴 플랫폼 |
| 유입 채널 귀속 | §5-3 판정 순서 (추천 > 메타 광고 > 토스 > 소셜 > 자연·직접) | LTV 와 같은 축 |
| 확인용 코호트 | 탐색·사후 가설은 **그 가설을 만든 기간 밖의 코호트로만 판정** (지금은 9/28 이후 진입) | B3-b·S1·T1 에 쓰던 원칙을 공통 규칙으로 |
| 실험 코호트 | E1·E2 는 배정 시점(첫 방문 기기 해시) 기준 — 진입 코호트와 별개로 사전등록 정의를 따른다 | 처치가 진입 자체를 바꿀 수 있어서 (E2) |

**기존 수치:** 활성화 퍼널(447/203/155/79, 39%)은 이미 이 규칙과 같다 (M5). 참여 LTV(§5-3, 첫 진입 7/27~9/13 160명)·주제 문장(168명)·첫 5분 진단(203명)은 산출 당시 베타 테스터를 포함한 모집단이라 그대로 두고, 재계산은 §8 남은 일로 둔다.
