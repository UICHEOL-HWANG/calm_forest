# G1 이상 탐지 — 관리도로 데이터 오염을 자동으로 잡을 수 있나 (G0 초안, 결과 보기 전)

**작성** 2026-10-12 · 상태: ✅ G0 서명(2026-10-12) · G1 통과 · 결과가 나와도 기준은 고치지 않는다
연결: `analysis-candidates.md` §1-G (G1) · M5 공식/원본 두 벌 출력 · 페르소나 실행 기록 `tools/persona-sim/runs/`

## 0. 분석 목적
1. **문제** — 지표가 오염돼도 사람이 우연히 보기 전에는 모른다. 9/28 주 원본 WAU 418(공식 15)은 페르소나 시뮬레이션 때문이었고, 9/7 주 코인 순증가 384 는 베타 번들 때문이었는데, 둘 다 나중에 손으로 찾았다
2. **왜 중요한가** — 지표 SQL(M5)이 매주 돌기 시작하면 오염된 숫자가 그대로 대시보드·의사결정으로 간다. 광고 집행 뒤엔 봇·크롤러 유입도 늘어난다
3. **무엇을 결정하나** — 원본 지표에 관리도 경보를 붙여 운영할지(파이프라인에 넣을지), 넣는다면 평균±3σ 와 중앙값±MAD 중 무엇으로
4. **성공 기준** — 날짜가 확실한 사고 2건을 경보가 시작 2일 안에 잡고, 사고 밖 오경보가 운영 가능한 수준인지 숫자로 말할 수 있다
5. **범위 밖** — 원인 자동 분류 · 실시간(시간 단위) 탐지 · 사고 복구

## 3. 방법
- **주 방법 — Phase II 개인값 관리도(평균±3σ):** 날 t 의 기준선 = 직전 14일(이미 경보 난 날은 기준선에서 뺌, 가림 방지) · 경보 = x_t 가 평균±3σ 밖 (양쪽) · 첫 14일은 준비 기간
- **비교 방법 — 중앙값 ± 3 × 1.4826 × MAD** (같은 14일 기준선)
- **음성 대조:** 같은 관리도를 **공식** 값(페르소나·개발자·베타 제외)에 돌려 I1·I2 기간에 경보가 사라지는지 — 필터가 오염을 걷어낸다는 확인

## 4. 판정 기준 (결과 보기 전 고정)
- **AD1 탐지:** I1 을 M1 이, I2 를 M2 가 사고 시작일부터 2일 안에 경보 → 둘 다면 **지지**, 하나면 **부분**, 없으면 **반대**
- **AD2 오경보:** 사고 기간(+끝난 뒤 2일) 밖 경보가 지표당 감시일 30일에 1회 이하 → **운영 가능** · 넘으면 **운영 불가(임계 조정 필요)**. 오경보 날짜는 배포 이력과 대조해 '설명되는 변화'와 '설명 안 됨'으로 나눠 보고하되, **판정에는 모두 오경보로 셈**
- 방법 비교(평균 vs 중앙값)는 같은 기준으로 둘 다 보고, 운영 권장은 AD1·AD2 를 모두 통과한 쪽 (둘 다면 오경보가 적은 쪽)

## 5. 미리 밝혀 두는 한계
- 사고가 2건뿐 → 탐지율은 사례 확인이지 추정치가 아니다
- 요일 효과·추세(코인 첫 루프 9/5 같은 구조 변화)는 따로 모형화하지 않는다 → 구조 변화일에 '설명되는 오경보'가 날 수 있다
- 하루 기기 수가 작아(수십) σ 가 크다 → 작은 오염은 못 잡을 수 있다
- 페르소나 I1 기간 끝 시각은 실행 기록 기준, 그 뒤 남은 탭 꼬리 이벤트는 고려 안 함
